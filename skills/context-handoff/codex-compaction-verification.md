## 核心证据：压缩后历史的角色构成

22 次压缩，每次 `payload.replacement_history` 的构成：

```
 1  8 条    compaction×1  user×7
 2  22 条   compaction×1  developer×3   user×18
 …
22  158 条  compaction×1  developer×17  user×140
```

**没有一条 assistant。** 一次都没有。

所以压缩后送回模型的历史 = 1 份加密摘要 + developer 指令 + **全部 user 消息**。
助手说过的每一句话——包括「X 已修复」「Y 已完成」——**原文全部消失**。

这坐实了 [openai/codex#5799](https://github.com/openai/codex/discussions/5799) 的核心说法。

### 但要打一个折扣

摘要条目长这样：

```json
{"type":"compaction","id":"cmp_02ad0f…","encrypted_content":"gAAAAABqnigAHSqy…"}
```

**加密的。** 所以只能确认「助手原文没了」，**无法确认「摘要里有没有补回完成信息」**。
我之前说"摘要丢掉了完成信息"——这一步我没有证据，收回。

## 新发现：压缩会越来越不管用

user 消息数在 22 次压缩中单调递增：**7 → 18 → 29 → 64 → 93 → 140**，从不被丢弃。

意思是**每次压缩只能砍掉助手轮次和工具输出，user 消息是地板，而地板一直在涨**。
后果直接体现在压缩间隔上：

| | 平均间隔（ordinal） |
|---|---|
| 前 5 次 | ~580 |
| 后 5 次 | ~346 |

**压缩频率涨了约 40%。** 越到后面，压一次能腾出的空间越少，撑不了多久又满。
这就是所谓「压缩循环」的机制——不是玄学，是地板在涨。

## 键名与 hook 的更正

`model_auto_compact_token_limit` 不在当前官方 config schema 里。
但你的日志里出现了 `compact_token_limit_scope`，schema 里对应 `AutoCompactTokenLimitScope`
（取值 `total` / `body_after_prefix`，决定按哪部分计入阈值）。**机制在，键名变了。**

schema 里还有两个我之前没提的：

- `PreCompact` / `PostCompact` —— **可以挂 hook**
- `experimental_compact_prompt_file` —— **可以自定义压缩时给模型的指令**

后者很关键：既然助手轮次必然被丢，那能补救的地方就是让摘要指令
明确要求保留「已完成清单」和「不许改动的文件」。

## 结论与建议

1. **别等自动压缩。** 它保证丢掉助手的全部原文，而你的长会话里"做完了什么"恰恰只存在于助手轮次。
2. **按 `/status` 显示值定阈值就行**，它是准的。压缩在 ~93% 触发，所以 70–75% 已用时主动交接是合理的。
3. **优先配 `experimental_compact_prompt_file`**，把「保留已完成清单 / 保留禁改文件清单」写进压缩指令——这比事后 handoff 更靠前。
4. **`PostCompact` hook 可以做兜底**：压缩后自动把完成清单重新注入。
5. 405 MB 那个文件可以删了（`/resume` 用不到这么老的会话）。

## 追加实测（2026-09-14 晚）

258K **不是 Astra 的上限，是 Codex 的会话工作预算**。模型本体约 1.05M。

以下两个顶层键把预算开到 1M，`/status` 确认 `Context window: 100% left (0 used / 1M)`：

```toml
model_context_window = 1000000
model_auto_compact_token_limit = 900000
```

验证环境：`gpt-6-astra` / Pro Lite 订阅 / 本地代理 `127.0.0.1:8788`。

两条被推翻的二手说法：

- 「这两个键只对 gpt-5.6-sol 有效」—— 对 Astra 同样生效
- 「订阅制用户被截到 ~360K」—— Pro Lite 实测全开 1M

结论：**别信绝对 token 数，按百分比判断**。预算可配置、随模型和客户端版本变化。
