# after_design — 架构完整性检查（Go 后端）

**档位**：Step 1 硬阻断，其余软警告。先查项目覆盖版本 `docs/hooks/after_design.md`。

## Step 1 — 接口定义四要素 [硬阻断]

Design 中每个新增或变更的接口（HTTP / RPC / MQ 消费）都必须有：

| 要素 | 示例 |
|---|---|
| 路径/方法 或 RPC 方法名 / topic | `POST /api/v1/order/cancel`、`OrderService.Cancel` |
| 请求参数 | 字段、类型、必填、校验规则 |
| 响应结构 | 成功时的数据结构 |
| 错误码 | 至少覆盖核心失败场景 |

缺任一项 → 硬阻断。接口是前后端/上下游联调的合同，少一项就会在联调时返工。

启用了 taotao-contract 切片时，以 Design 中「接口契约（taotao-contract）」章节的契约 diff 为准检查这四项；契约文件本身通过 lint 即视为字段与类型完整。

## Step 2 — 数据与一致性 [软警告]

- 新增表/字段有 migration 方案和回滚方案；新查询有索引说明；
- 写操作的幂等方案（幂等键、去重表、状态机守卫）；
- 跨表/跨服务操作写清事务边界，分布式场景说明最终一致性手段（outbox、补偿、对账）；
- 缓存：读写顺序、失效策略、穿透/击穿防护。

## Step 3 — 健壮性 [软警告]

- 每个外部依赖：超时时长、是否重试（重试是否幂等安全）、降级/熔断；
- context 是否从入口一路传到底；
- goroutine：谁启动、何时退出、panic 是否 recover；
- 配置项与开关：新增配置的默认值、灰度开关。

## Step 4 — 可观测性与安全 [软警告]

- 关键路径的日志字段（trace_id、业务主键）、metrics、告警；
- 鉴权与越权校验；敏感字段脱敏/加密。

## Step 5 — 技术栈一致性

- 引入的新依赖与 `docs/knowledge/tech.yaml` 冲突 → 软警告；
- 命中 `docs/rules/tech-selection.md` 中的禁止替代方案或 `forbidden.md` → **硬阻断**。

## Step 6 — 高风险节点隔离 [软警告]

ARD 中标注的每个高风险节点，Design 里都要有对应的隔离方案（开关 / 兼容 / 降级 / 灰度）。

## 输出

通过：

```
✅ 架构完整性检查通过（backend-go）
- 接口: N 个，四要素完整
- 数据: migration ✓ 幂等 ✓ 事务 ✓ 缓存 —
- 健壮性: 超时 ✓ 降级 ✓ goroutine ✓
- 可观测/安全: ✓ / ⚠️ …
- 高风险节点: N 个已隔离
```

硬阻断：

```
🚫 架构完整性检查未通过，不能进入 Plan：
- POST /api/v1/order/cancel 缺少错误码定义
恢复：补全后我重新输出 Design 给你确认。
```

软警告：列出问题，用户回复「继续」进入 tt:plan。
