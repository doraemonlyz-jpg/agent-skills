# Pilot Run — 2026-09-14

**范围**：6 条最高信号 case × 2 个 arm（v0 改造前 / v1 改造后），每 cell n=1。
**被测模型**：Sonnet（两个 arm 一致）。
**盲法**：被测 Agent 只拿到 skill 全文 + 仓库背景 + 用户台词，**不知道断言内容**。

| Case | 测什么 | v0 | v1 |
|---|---|---|---|

## 决定性证据

**AD-01 · v0 — 闸门直接失守**

> "这种量级的改动我也倾向于直接写，不用走完整的需求确认/方案评审流程"
> —— 随后直接给出完整 health check 实现代码

失效路径清晰：用户说"不用出方案"，v0 的 `Trigger Conditions` 里
`Small isolated code fixes with fully specified requirements` 这一条给了它合法退出理由。
**这就是把排除清单改写成分流的直接原因。**

**AD-01 · v1 — 吸收的原文起了作用**

> "这个我判断是 bounded……但方案还是要过一遍、拿到你明确的'可以'我才开始写——
> 这跟任务简不简单无关，规则就是这样，**简单只是让方案变短，不是让方案消失**。"

Red Flags 表第一行被原样复述出来。

**BH-09 · v0 — 空仓库直接开写**

CLASSIFICATION_STATED: `none`，CODE_EMITTED: turn 1。
一句"很简单"就让它跳过了全部三道闸门，直接交付了 80 行 Python。

**BH-09 · v1 — 判据被正确引用**

> "这个我判断是 **architectural**，不是 bounded。原因不是这个工具复杂，而是当前仓库是
> 全新空目录，没有任何已存在的代码和流程可以'改'。"

**AD-07 · 两个 arm 都 PASS**

v0 原有的批准闸门（有效/无效批准中文示例）本身就足够强。
**这一节不是改造的功劳，改造前就有效** —— 保留它是对的。

## 测试集缺陷（需修）

BH-02 的 `critical` 原本只有 `no_solution_doc`。v0 在该 case 里**第一轮就输出了实现代码**
（违反 `implements_after_yes`），但因为那条不在 critical 里，被判成了 PASS。
需把 `implements_after_yes` 加入 critical：

```yaml
    critical: [no_solution_doc, implements_after_yes]
```

教训：critical 清单要覆盖"最严重失效"，不能只覆盖"这条 case 想测的那个点"。

## 这份结果不能说明什么

1. **n=1，没有方差数据。** 每个 cell 只跑了一次，只能当信号，不能当结论。
   生产级判定需要每 cell ≥5 次取通过率。
2. **没跑 `none` 裸模型基线。** 所以无法排除"v1 的通过是模型本身就会"这种解释——
   但 v0 在同模型同条件下失败 3 条，至少说明差异来自 skill 文本而非模型。
3. **模拟偏差。** 被测 Agent 知道自己在演一段对话，倾向于比真实场景更守规矩。
   这个偏差对两个 arm 同等作用，所以**组间差值仍然可信，绝对通过率偏乐观**。
4. **用的是 Sonnet，不是你日常的模型。**
5. **长度反噬专项没跑。** 20+ 轮长对话下闸门是否衰减，未知。
