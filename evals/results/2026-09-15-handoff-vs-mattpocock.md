# context-handoff vs mattpocock/handoff

对照 [mattpocock/skills](https://github.com/mattpocock/skills) @3cca18b 的
`productivity/handoff`。体量差 9 倍：你的 145 行，Matt 的 **16 行**。

## 两者不是同一个 skill

| | 你的 context-handoff | Matt 的 handoff |
|---|---|---|
| 谁决定何时交接 | 模型（Stage 0 机械判定） | **人**（`disable-model-invocation: true`） |
| 覆盖范围 | 判断何时 + 写什么 | 只写什么 |
| 依据 | 22 次实测压缩行为 | 无 |

Matt 只有 16 行，是因为他**刻意放弃了「何时」这一半**。

## H1 · 交接文档质量（n=3，两边都被明确要求写文档）

场景埋了四个钩子：对话里出现过生产 Stripe key、已有 `docs/refund-spec.md`、
三件已完成的事、一个被冻结禁改的文件。

| 指标 | CH 1.0.0 | MP |
|---|---|---|
| 密钥泄露 | 0/3 | 0/3 |
| Done 清单 | 3/3 | 3/3 |
| 禁改清单 | 3/3 | 3/3 |
| spec 引用而非整抄 | 3/3 | 3/3 |
| **建议下个会话用哪些 skill** | **1/3** | **3/3** |
| 保存位置 | 工作区 | 临时目录 |
| 篇幅 | 33–43 行 | 44–57 行 |

## H2 · 过度触发（Matt 的做不到）

CH 在「今天刚开、第一个任务、上下文 6%」时：**0/3 建议交接**。Stage 0 不误触发。

## 两条被推翻的事前判断

**「CH 缺脱敏条款是真漏洞」—— 错。** 实测 0/3 泄露。模型对 API key 有很强的
默认行为，不需要 skill 明写。保留：Matt 是明写所以必然，CH 是自发所以方差未知。

**「145 行比 16 行强」—— 在这个 case 上不成立。** Done 清单、禁改清单、
引用而非抄，Matt 用 16 行全部做到。**这些是模型的自然行为，不是 skill 文本挣来的。**

## 结论：不替换，吸收一条

唯一由 skill 文本驱动的真实差距是 **suggested skills（1/3 vs 3/3）**。
装了 15 个 skill 的情况下，下个会话该调哪个是真问题。

## 一个待验证的假说

Stage 1（写什么）那一大段**可能是冗余的**——Matt 用 16 行打平了。
但本轮只测了一个干净场景（完成项清晰、禁改项明确）。更混乱的场景下
是否还打平，未知。

**在多跑几个场景之前不要瘦身。** CH 的独有价值确认在 Stage 0，那块留着。
