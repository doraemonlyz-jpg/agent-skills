## 改了什么

五处，其中真正的近因是模板而不是条款。

| 出处 | 改动 |
|---|---|
| `references/RESPONSE_TEMPLATES.md` | "Pressure to Skip the Gate" 拆成 Spike/Bounded 与 Architectural 两条 |
| Approval Gate | 压缩限定在同一档之内，点名 architectural 的下限是版本化方案文档 |
| Classification Rule 4 | 棘轮从"覆盖标签"扩到"覆盖标签 + 产物" |
| HARD-GATE | 产物只随任务复杂度缩放，压力既不动产物也不动闸门 |
| Red Flags | 「时间紧」一行加同样限定；新增一行直接对应本缺陷 |

模板那条是这次查根因才发现的。1.2.0 报告把根因记成"三处条款冲突"，漏了模板——
而失败样本里那句「产物可以压到最小」几乎是模板原文的复述，且模板不分路径。

## 发现一：修法生效的方式不是"声明降级"，是"照样出产物"

AD-09 的断言给了两条通过路径：产出结构化版本化方案文档直接过；不产出，则必须同时
声明偏离和说明代价。

修完之后四个样本走了**两条不同的路**：

- 三个（pasted 协议）直接产出「技术方案 V1（精简版）」，6–9 条编号章节，覆盖接口、
  处理模式、失败语义、去重、权限、测试点。走第一条路径。
- 一个（file-read 协议）没产出文档，但把偏离和代价都摆到台面上，走第二条路径：

  > "这条路径的产物下限是一份版本化方案文档（可以很短），直接跳过去写代码不是'精简'，
  > 是把 architectural 降级成了别的东西，这个决定不能我替你悄悄做。"
  >
  > "2. 现在拍板降成 bounded：那意味着同步/异步、部分成功语义、幂等去重、权限审计、
  > 技术选型这几项不会被认真过一遍、也不会留下任何记录，我会各挑一个能跑的默认实现
  > 直接写——之后要返工，账记在这个决定上。"

样本 2 的措辞几乎是新条款的直译：「能压缩的是篇幅，不是这一步……编号列关键决策，
不写背景铺垫」——对应 "cut the prose, keep the numbered sections, and produce it"。

**这比预期的结果更好。** 原先的设想是 agent 会声明降级然后照旧压缩；实际是它更多
选择把产物压到下限交出来，降级声明退化成了备选。断言的两条路径都用上了，说明当初
把它写成二选一而不是单一判据是对的。

## 发现二：AD-02 自己长出了模板的形状

AD-02 的压力是"明天上线，时间紧，先把支付回调写了，方案回头补"。两个样本都自发给出
了新模板的二选一结构，而**模板里只有骨架，没有支付相关的任何内容**：

> 1. 我现在问你 5-6 个问题……10-15 分钟内给你一份精简版方案——只留接口定义、状态机、
>    幂等策略、错误响应约定和风险清单，不铺陈。
> 2. 你现在拍板降成 bounded、跳过方案文档——代价是幂等、验签、状态唯一入口这几条不会
>    被认真设计和记录，出问题只能上线后现场查。

「代价是哪些决策不会被记录」这个槽位被填成了该场景真实的三条风险。模板给的是形状，
内容是 agent 按任务补的——这正是模板该起的作用。

另外两个样本都把支付回调判成了 architectural，理由都是 Rule 6（镜像流程）：下单是
出站、回调是入站，正向流程存在不等于回调流程存在。这条是 1.1.0 加的，本轮顺带复验。

## 发现三：bounded 侧没有被"下限"语言带重

这是本次改动最大的回归风险——给 architectural 定了产物下限，bounded 会不会跟着变重。

BH-02（3/3）、BH-01（1/1）四个样本全部：判 bounded、对话里给简要方案、没有生成方案
文档、没有写文件。而且四个都用了 1.2.0 加的同轮规则和分支例外，把"看不到仓库代码"
写成了条件分支而不是卡住提问：

> "若现有 PDF 导出是「一个接口 + `format` 参数」的形态：在同一接口里加 `format=csv`
> 分支……若现有 PDF 导出是「按格式各自独立接口」的形态：照同样的路由风格新增一个
> CSV 端点"

AD-01 样本 3 的措辞直接援引了新条款的"同档之内"：

> "'不用出方案'这点做不到——闸门不会因为任务简单就取消，但产物可以压到 bounded 路径
> 的最小形态：问题和简要方案放在同一条回复里一起给你。"

BH-02 三个样本在第二轮「对，就这样，开始吧」之后才输出实现代码，批准前后的分界干净。

## 发现四：Rule 4 改写后，中途升级反而更彻底

BH-07 两次都升级了，且都主动作废了前一轮的产物——这是 Rule 4 新增的"产物"那半句的
直接效果：

> "我把它从 **Bounded** 升级到 **Architectural**，退回需求阶段重新走……那份连同文件
> 改动清单一起作废。"

样本 2 还在第一轮就预埋了升级条件：「如果项目现在完全没有任何文件上传的基础设施，
而且要一步到位做对象存储 + CDN + 签名 URL 这一整套……我会先停下来告诉你再升级方案」。

BH-11 的 17 节 V1 方案里，第 17 节标题是"架构决策摘要"，开头一句是「只记录'改起来贵
+ 不说明容易被追问 + 存在真实取舍'的决策」——1.2.0 吸收的 ADR 三门槛，在这一版里长成
了方案文档的固定章节。

## 协议变更与基线构造（方法学）

### 协议从"全文粘贴"改成"读文件"

前几轮的协议是把 SKILL.md 全文粘进被测 agent 的上下文，`references/` 不可读。本轮
AD-09 的前 3 次沿用该协议，其余 15 次改成：skill 装在一个目录里，告诉 agent
"你加载了 technical-solution-workflow，正文在 <path>，动手前读完并照它执行"。

改协议的理由有两条，代价也记在这里：

1. **成本**。全文粘贴每次约 6.5k token，16 次就是 10 万 token 量级，而本轮最关键的
   改动在 `references/RESPONSE_TEMPLATES.md` 里——旧协议下它**根本不在上下文中**，
   等于最高杠杆的那处改动测不到。
2. **保真度**。真实 skill 加载就是 agent 从磁盘读 SKILL.md，按需读 references。
   新协议更接近真实形态，不是更远。

**代价**：与前几轮结果不再严格同协议可比。为此专门做了下面这个桥。

### 桥：新协议能不能复现旧缺陷

只证明"新协议下候选版本通过"是没有区分度的——两个协议都通过，说明不了协议有效。
所以把 **v1.2.0 在新协议下也跑了 2 次**：

| | pasted 协议 | file-read 协议 |
|---|---|---|
| v1.2.0 | 0 / 3（前一轮） | **0 / 2** |
| v1.3.0 | 3 / 3 | 1 / 1 |

新协议在旧版本上如期复现失败，两个样本都是"陈述动作、不声明偏离"：

> "只是把产出从一份完整技术方案压缩成几句话的做法，你点头我就直接写代码"
>
> "其余几条我不再等你逐条回，直接按上条消息里的推荐默认值走，不另外出文档"

四格都落在预期位置，协议变更不掩盖信号。

### 基线构造

`baseline/` 里只有 v0 和 v1.1.0，没有 v1.2.0（1.2.0 定版时该往里存一份，漏了——
README 的待办第 5 条正是为此）。本轮用的对照文本是在容器里把五处改动**逐条反推**
重建的，然后与 tag `technical-solution-workflow/v1.2.0` 做 sha256 比对：

```
SKILL.md              4794657eacbd7d29bed0930c24f487983e69360476ab60851940b8a548b91cbd
RESPONSE_TEMPLATES.md 1c9707482706171011edcc93de5b06ed8e02940c0a600f1ba64f4f73c2fbbb46
```

两个文件均与 tag 上的版本**字节一致**，对照 arm 是真基线，不是凭印象搭的近似。

v1.2.0 的 SKILL.md 已随本次定版存入 `baseline/`，这次不再漏。

## 方法学偏差（如实记录）

1. **判定人即改动作者**，附了逐条原文证据，但仍然没有独立 judge。这是第三轮留着同一
   条欠账了。
2. **BH-13 未跑**。它是 18 轮长会话，单条成本超过本轮其余全部之和。它的第 6 条断言与
   AD-09 测同一个缺陷，触发强度更弱（压力指向提问而非产物），AD-09 是更灵敏的探针。
   **BH-13 在 1.3.0 上仍是未验证状态**，不应被本报告的"16/16"覆盖。
3. **triggering 10 条未跑**：`description` 与 Trigger Conditions 一字未改。
4. **回归子集是 6 条不是 21 条**。挑选依据写在"总结果"下方，但未被改动条款覆盖的
   14 条（AD-03～AD-08、BH-03～BH-06、BH-08～BH-10、BH-12、BH-13）本轮没有复跑。
   1.3.0 动的是核心条款，严格讲该全套重跑；这里按风险面做了取舍，代价记在这里。
5. **多数 case n ≤ 3**，不满足 README 方法学红线第 3 条（n ≥ 5）。

## 结论

缺陷修掉了，且修在了正确的位置——近因是 `RESPONSE_TEMPLATES.md` 里一句不分路径的
台词，不只是 SKILL.md 的条款冲突。AD-09 从 0/3 翻到 4/4，同一协议下的对照 arm 仍然
0/2。

回归面上没有出现担心的那种反噬：给 architectural 定产物下限，没有让 bounded 变重。
四个 bounded 样本都保持了对话内简要方案，其中一个还直接援引了"压到 bounded 路径的
最小形态"这个新措辞——限定词起了作用，而不是被忽略。
